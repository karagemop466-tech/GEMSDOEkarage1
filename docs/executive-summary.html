Why we will not hand you a "beats 0.2778" file today

We can explain, with high confidence and full citations, why GEMSDOE32's 0.2778 claim happened (see the analysis in research/sibling_site_audit.md): the distance-weighted Tversky metric rewards a small number of high-confidence points placed within 300 m of known fault geometry far more cheaply than it penalizes being wrong elsewhere, so a sparse "pack dots near catalogue-adjacent structure" strategy can reach ~0.25–0.28 on a self-reported, non-organizer holdout — while the sites' own off-catalogue diagnostics for the same files collapse to ~0.04–0.09, implying that strategy mostly rediscovers the existing catalogue rather than finding genuinely new faults. The real, organizer-confirmed public leaderboard (fetched live, no login needed: leaderboard) tops out at 0.4544, 40–65% higher, almost certainly from dense, trained probability models (like the official reference U-Net) that generalize past the catalogue.

Generating a genuinely better file requires the real training_features.tif/labels.tif, which this environment cannot download (no DrivenData login configured here, and the sandbox's network allowlist does not include drivendata.org, Dropbox, or USGS/OpenEI's binary hosts — verified live, see LIMITATIONS.md). We built the entire pipeline (metric, grid, writer, validator, tests) so that the moment that one credentialed download happens, a real candidate can be engineered, holdout-tested, and submitted the same day. Five specific, ranked, sourced ideas to try first are in research/hypotheses.md.

How to make a submission to the contest

  1. Enroll. Create a free DrivenData account and click "Compete!" on the competition page.
  2. Download the real data. From the data tab (requires login), save training_features.tif, labels.tif, sample_submission.tif, and 1m_DEM_links.csv into this repo's data/ folder.
  3. Check the grid. Run python scripts/prepare_data.py. It compares the real files against this repo's cached grid constant (src/gems/grid.py) and tells you immediately if they don't match — fix the constant from the real file, never the other way around.
  4. Build a candidate. Engineer features and train/fit a model (start from the reference U-Net solution or implement a hypothesis from research/hypotheses.md).
  5. Score it honestly, offline, first. Use src/gems/metric.distance_weighted_tversky_index against a spatially-blocked, whole-fault-segment holdout (never a random pixel split — that leaks). Run the leakage canary on every new feature alone (reject anything scoring >0.90 AUC by itself, it's probably leaking).
  6. Write the file. Use src/gems/submission_writer.write_submission, which guarantees a single-band float32 GeoTIFF, correct CRS/shape/transform, and every pixel clipped and sanitized into [0, 1] — this is what prevents the "Predicted values must be in range [0, 1]" error.
  7. Validate before you click submit. Run python scripts/validate_submission.py path/to/your_candidate.tif. Do not upload anything that doesn't print all_checks_passed: true.
  8. Upload it. On the competition's "Submit" page, choose your .tif (or a .zip containing exactly one GeoTIFF). Give it a unique submission name (e.g. h-a-coulomb-tendency-v1) and, in the optional Note field, a short (≤140 character) description a teammate could use to tell it apart later (e.g. "H-A Coulomb slip/dilation-tendency filter on gravity+magnetics ridges, alpha=0.2/beta=0.8 holdout DTI 0.xx").
  9. Pick your one final submission carefully. Per the official competition structure, you choose a single submission for scoring across both the Initial and Final Prize Rounds before the deadline, without knowing your private-test performance — don't spend your pick on an unvalidated idea.
