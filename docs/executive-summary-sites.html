WHY GEMSDOE32 B2 SCORED 0.2778 — AND WHY IT CANNOT BE COPIED

The mechanism and its limit

All nine focus submissions are built on the same lineament lattice (the 13GEMSDOE covering lattice plus catalogue anatomy). They differ only in dot count. Reported score is almost perfectly inversely monotone in dot count (Spearman −0.967, n=9): every additional dot past the break-even point lowers DTI because its marginal truth credit is below alpha·DTI/(1−DTI) ≈ 0.0769 at s=0.2778. B2 found the dot-count sweet spot for this lattice.

Copying B2 is not a strategy: it is already submitted, not unique (100% overlap with its parent GEMSDOE25), and the catalogue holdout scores it below random (0.0048). Beating 0.2778 requires either (a) a surface with ~1.3–1.9× the per-dot truth rate of B2, or (b) independent expert fault traces outside the catalogue. Neither has been demonstrated in this repo.

SUBMISSION PORTAL ERROR — "PREDICTED VALUES MUST BE IN RANGE [0, 1]"

Cause and fix

The DrivenData portal rejects a GeoTIFF when any pixel value fails a naive range check. NaN fails this check because NaN >= 0 and NaN <= 1 are both false. The organizer's own example uses NaN outside the bounds, which is legitimate for geospatial data, but a naive client-side validator can still reject it.

Fix: write zeros (0.0) outside the footprint instead of NaN. Every file generated by this repo's build scripts uses zeros outside the footprint, so np.all((a >= 0) & (a <= 1)) is true for the whole array — including outside the footprint — and the portal's range check passes. The file above (…-zeros.tif) has 0 NaN pixels and passes both the naive whole-array check and the NaN-aware check.
